# Context-IR 多参考图：配置、制作与排错

## 在网页中使用

1. 在「系统设置 → 服务档案」配置并测试本机 Context-IR 视频服务，项目的视频用途采用该档案。完整部署见 [本地推理节点部署](local-inference.md)。普通 ComfyUI 或聊天 API 能连通，并不代表 Context-IR 节点已经部署。
2. 导入 Word，进入「项目工作台」。在人物参考图下方展开「固定产品／道具参考图（可选）」。上传原图或选择图库产品，再明确绑定需要使用它的分镜。
3. 同一商品的正面、侧面、开盖等照片保存在同一个产品档案中。不同商品建立不同档案；同一文件夹并不能证明商品身份相同。人物照片用人物参考入口保存，不要绑定为商品。
4. 批量产品引用区按服务返回的预算显示可选数量。当前产品制作选择支持每产品最多 8 张；Context-IR 原生工作流人物、产品、场景合计最多 9 张图片，另支持最多 3 段参考视频。图库每产品可以保存 32 张图片，保存数量与单镜推理预算不同。
5. 保存引用，选择 Fast／标准／高质量，开始制作。三档分别编译至真实 4／20／30 步图。Fast 需要配套 4step LoRA；只改步数无法替代它。

图片数量来自动态集合，Schema 没有固定 image1／image2 槽位。超出实际服务预算时明确报错，程序不会静默截取前两张或丢掉第三张。

## 图片如何进入模型

```text
网页多选 → API 上传与完整原图保存 → 分镜明确选择的图片 ID
 → 原文件解码、尺寸和 SHA256 检查
 → 本地 Qwen 逐图文字观察与结构化视觉分析
 → 按明确身份声明进行商品跨图验证与归组
 → 全部分析结果和原始镜头要求融合
 → 原生 Context-IR Schema、引用绑定和语义质量门
 → 冻结三档工作流 → 释放辅助模型 → H3 → 画质处理 → 自动合成
```

每张图片独立保留 `image_id`、来源、SHA256、商品／人物 ID、用途、尺寸、备注和分析状态。同一商品多视角按明确产品 ID 归组；未知关系保持未知。照片内的持物手、背景装饰等观察保存在原始分析中，不会仅因出现在商品照片里就成为新场景必须重现的人物或商品。

只给已经通过图片身份验证的商品补齐已有文字的引用标记；不编造外观、不删用户文字，原有质量门仍执行。人物引用关系来自用户明确声明，不能把编译通过称为自动人脸身份鉴定。

Word 中的文字人物资料即使尚未生成标准脸，也会作为明确的剧本输入传给 Context-IR；不会因人物版本仍为草稿而变成空描述。这不改变人物版本的审核状态，也不表示已有照片身份保证。包装开合、内含商品等按本镜要求表达，参考图中摆在包装旁的商品不要求在拆封前提前露出。

文字人物外观与表演也进入原生 `Brief.constraints`。手部特写后来露出人物面部时，仍应沿用 Word 的人物资料，不能让商品照片内的持物者取代该角色。没有角色照片时，这提供的是文字约束，仍需检查视频实际外观。

原生配音的对白通过已校验的原生 `Brief.dialogue` 字段传递，不把 JSON 转义后的台词拼进 `@speaks` 文法。原台词的字符、语言和群体合唱保留并写入 `native-typed-dialogue.json`；原生逐字对白质量门继续执行。编译通过仍须检查实际声音、说话人和口型。

明确绑定的 Word 道具规格和本镜状态也进入原生 `Brief.constraints`，不会只埋在长段场景 JSON 中。修复调用保留完整台词和实际说话人表，补齐已在正文定义的文字人物标签；不会把“缺少人物照片”误当成这些人物标签不存在。模型仍须写出修订后的完整 IR，全部原生校验再次执行，适配器不替模型拼接对白来获得通过。

对白修复使用完整的原生 `<d>…</d>` 语法，并按明确的参演者 ID 查找说话人，避免模型复制自定义 XML 或误按图片顺序分配声音。同一主体若被模型拆成多行相同的 `fully_preserved` 保留说明，只有在镜头归属明确时才无损合并；保留全部描述和图片引用。冲突的保留方式仍由原生质量门拒绝。

修复请求在候选正文之后再次列出实际失败项。保留区语法出错时，读取并核对已安装编译器 `ref-en.txt` 的固定哈希，将原生保留区规范提供给模型；不把视觉 Subject 改报为 Audio，也不替模型删除冲突行取得通过。规范版本变化会明确拦截，避免使用猜测的语法。

原生修复接口没有携带 `Brief.constraints`，因此适配器会把当前真实 Brief 和调用方的完整约束重新提供给修复模型，并保存约束列表及哈希。包装关闭、人物资料和服装不能在修复引用错误时丢失。引用某个商品身份也不表示该商品必须露出；已有的封装、遮挡或容纳关系须沿用当前镜头要求，在正文中明确引用该 Subject，不得为通过绑定检查提前拆封、编造容纳关系或隐藏原本要求可见的商品。

若实际失败项为主体引用绑定，纠错模型通过已有的本地受约束 JSON 接口输出修订段落。如果质量门已经确认定义区存在唯一正确绑定、只缺正文引用，并且其他失败项也仅涉及该段对白或当前状态，则让模型重写完整的详细描述；已有的封闭容纳关系同时要求摘要保持一致时，也由模型重写摘要。其余段落保留原候选的模型文字。其他绑定问题仍要求模型输出六个完整段落。适配器只添加原生段落标题和分隔符，不插入商品引用、动作或外观描述；少段、重复键、非 JSON 或空段落都会明确失败。随后继续执行全部原生校验。两轮原生纠错采用不同的有界采样参数，避免相同低温度和种子反复复制错误正文；不会增加重试轮数，也不改变逐图分析和首次写作的参数。

单段修复将已核实的现有 Subject ID 设为 JSON 字段的实际允许值，模型写出各 ID 前后的连续正文；适配器按顺序连接模型返回的全部文字字段和 ID 字段。ID 数量来自真实绑定错误，不按图片数固定为两个。同商品多角度仍只对应一个已核实主体。只有完整 JSON 和真实 EOS 都通过接口校验才会继续。该结构只能保证引用字段存在，不能替代后续原生语义门及实际画面检查。

对于已建立容纳关系且调用方要求包装关闭的镜头，新增校验会拒绝模型“包装仍封闭、内容物却被揭示”的实际矛盾表达。机械纠错也不能添加原候选没有的场景切换来处理重复台词；原生重复台词校验继续执行。发生这些错误时仍阻止 H3 提交，不会只因引用标记齐全就判定整个镜头合格。

隐藏物也不能在保留区继续标为需要完整呈现外观。该镜只对已明确隐藏的商品使用原生 `weak_reference`，保留类别／语义上下文，不承诺该物品在本镜受到完整外观约束；其余可见人物、商品和场景保留原策略。模型返回该商品的原生保留行字段，适配器只替换这一个已存在的行，保留其他行及原生强制的镜头作用域格式。三张或更多原图仍完整参与分析并保留来源，不能把这个处理称为删图后解析通过。遮挡是否真正落实仍须用生成画面验证。

如果原候选的动作与机位已经正确，缺陷仅为封闭内容物的引用／保留行、摘要中的错误揭示或缺少完整对白，修复改用小幅追加：保留原详细描述原文，模型只返回短引用说明、摘要和对应隐藏物保留行。这些状态字段只允许基于既有容纳关系的有限原生表述，不允许纠错模型另写外观或新动作，也不使用字符长度强行切断句子。缺少的完整原文对白作为受约束字段由真实本地模型接口返回，适配器核对后加入；已经存在的对白不重复添加。动作正文已有揭示内容物、重复对白或额外切镜错误时，禁止使用这种追加方式，仍执行原生完整纠错。多个主体出现在同一句容纳说明时不猜测谁被隐藏。原生两轮限额和所有质量门保持不变。

当前固定本地视觉档案是 Qwen3-VL-4B-Instruct、32K 上下文、每次接口最多 8 张图。逐图分析串行执行，单图最长边 1280、处理器像素预算 65,536–524,288；原始高分辨率文件保持不变。商品跨图验证按有界批次处理，9 图场景用重复锚点跨批核对。缓存包含原图哈希、模型与运行源码版本、分析提示版本、固定视觉采样种子及预处理／用途参数。

本机 `lm-format-enforcer 0.11.3` 对含双引号、反斜杠或换行的固定字符串存在字符解析问题：合法 JSON 的转义字符可能被拒绝，最终表现为输出达到上限或无可用后续 token。服务适配器对固定字符串使用完整 JSON 字面量解析，支持值前的 JSON 空白，并保留字符串自身的空白；不修改第三方文件、台词或原 Schema。结果继续按原 Schema 严格验证，修改后的固定值仍失败。真实接口回执的 `escaped_fixed_string_grammar=json-literal-v1` 可用于确认该修复已加载。

H3 专用的 Qwen3-VL 文本编码权重与完整视觉对话模型是两种用途，不能互相假定可用。不需要 OpenAI 或第三方云端接口，也不应重新下载已经通过校验的本地模型。

## 参考强度与限制

- 语义理解多张图、把照片直接作为 H3 视觉条件、最终外观准确，是三个分别验证的结果。编译成功不能证明 Logo 小字、手部动作或所有角度均准确。
- 实际 4 步多图出片测试仍出现过“包装盖与毛绒内容物融合、封套缺失”的画面失败。`weak_reference` 是语义指令，现有适配器没有据此证明逐商品潜空间降权或正确遮挡；不能将原生编译通过标为包装／内容物分离已验收。
- 同批成片的部分原生对白未通过实际逐镜 ASR 文字比对。保留完整原音轨只解决导出裁掉尾词的问题，不证明模型读准全部台词、说话人正确或口型准确；ASR 本身也可能识别出错，未通过项需实际播放复核。
- 单镜总量超过当前工作流 9 图预算会阻止提交。应明确调整分镜引用或换用经过验证的适配器；程序不会声称未送入 H3 的图片具有同等视觉约束。
- 参考视频默认提供摄影结构。商品或人物身份仍由明确绑定的图片决定；其他产品的视频不能自动成为当前商品的身份来源。
- 同一 GPU 上其他项目的模型也会占用显存。服务按请求释放自身模型，无法阻止另一个程序在生成中途占用 GPU。避免两个项目同时执行大型模型；不要把资源争用误认成第三张图片格式错误。

## 增量制作与历史任务

增量制作会复用文案、素材和制作参数相同的成功视频。审批状态、审批时间和预检提示的确认记录属于操作记录；这些字段变化时，程序会核对原始生成内容哈希和其余全部输入，再记录复用原因，不会重写旧任务快照。人物资料、台词、图片数量／顺序／哈希、引用备注、镜头版本或制作协议变化仍视为新输入。已驳回的镜头、当前预检错误和不可读的视频不通过这项兼容判断。

多项目同时运行时，「继续」在保留同项目互斥的同时，由线程执行完整的同步数据库事务。等待 SQLite 写锁不会阻塞正在完成另一项目派发的事件循环，不需要删除数据库或新建一条制作任务来恢复。继续操作只恢复原批次；同一批次已恢复后再次提交仍明确拒绝，避免重复派发。

自动合成中，有原生对白或合声的镜头保留完整源片声画。H3 会把请求时长对齐到可用帧数；把实际 4.458 秒的对白片段再裁回剧本 4 秒可能切掉最后一个词。导出回执记录保留完整原生对白的镜头及实际时间线，因此成片可能比剧本标称时长稍长。没有对白的镜头继续使用剧本时间线，旧剧本、原片、历史快照和旧成片保持原样。此项不保证模型实际读准台词，仍须检查成片声音。

## 根据证据排错

上传接口返回保存结果及 `trace_id`，审计事件记录浏览器声明数量、API 实际收到数量、持久化图片 ID／SHA256、错误类型。项目引用保存记录明确的图片 ID。生成日志用任务 ID 作为后续编译 `trace_id`，可沿相同图片 ID／SHA256 关联上传与生成。

本地编译输出中的主要证据：

| 文件 | 用途 |
| --- | --- |
| `reference-trace.jsonl` | 逐阶段、逐图来源与错误类型 |
| `reference-analyses.json`、`image-NNN.json` | 每张图的实际观察与缓存命中 |
| `product-reference-identity.json` | 实际图片商品身份核对，不以文件名代替 |
| `global-reference-fusion.json` | 明确身份归组及保留的照片上下文 |
| `native-typed-dialogue.json`、`native-typed-production-constraints.json` | 原文对白、道具规格和本镜状态的原生字段传递 |
| `repair-caller-context-NNN.json` | 完整对白、已有文字主体标签和原生修复调用的核对 |
| `repair-grammar-NNN.json` | 修复是否使用实际原生规范、规范哈希和真实失败项回传 |
| `structured-reference-repair-NNN.json` | 模型修订 JSON 的 Schema、原回复和格式化后哈希，以及实际替换的段落；不插入语义文字 |
| `small-reference-patch-NNN.json` | 小幅修复的原正文保留核对、模型返回哈希及完整原文对白块数量 |
| `caller-state-verify-NNN.json` | 关闭包装与揭示内容物的冲突、纠错新增场景切换等状态检查 |
| `retention-row-merge-NNN.json` | 相同主体保留行的无损结构合并，包含合并前后哈希和来源保留核对 |
| `request-*/request.effective.json`、`response.json` | 实际本机模型请求、回复及资源回执 |
| `reference-binding.final.json`、`source-gate.json` | 原生引用质量门、written／fallback 状态 |

这些文件可能包含私人图片数据和剧本文字，仅保存在本机，不应上传 GitHub。

本次水杯复现的早期失败发生在逐图分析之后的 `product_reference_validation._validate_reply`：视觉 JSON 重复列出同一实物，或臆测第二角度的品牌，导致身份校验拦截；不是第三个上传字段缺失。扩至六／八图后另复现了编译正文漏写主体引用标记的问题。对应修复位于项目自有节点 `reference_analysis.py`、`reference_fusion.py` 和 `local_h3ir_backend_profile.py`。不会把 `source=draft` 改报为成功，也不绕过 Context-IR。

应用代码更新后，推理主机的项目自有节点也必须更新；须先确认队列空闲并备份日志和历史，再按部署工具的校验结果更新。不要在模型任务执行中覆盖节点或清空 ComfyUI 历史。
